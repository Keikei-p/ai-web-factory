# AI案件分析 仕様

## 実装済みのローカル基盤（2026-09-22）

- `backend/src/analysis-types.ts`: 入力、出典付き事実、不足情報、確認事項、未採用提案、分析・仕様書の型。
- `backend/src/analysis.ts`: プロバイダーに依存しないサービス、入力の許可リストと除外処理、出力検証、ローカルスタブ、仕様書生成。
- `backend/src/analysis-routes.ts`: 保存・版管理・履歴・競合検出。Phase 1の既存テーブルにJSONを追記し、破壊的な移行は行わない。
- `frontend/src/AnalysisPanel.tsx`: 実行、生成、結果と過去版の表示、入力更新の警告。

この節は現時点の実装を記述する。以降のAI出力例・自動工程案は将来の仕様である。

### 入出力と外部通信

`AnalysisProvider.analyze(input)` は構造化した未知の出力を返す非同期契約。現在はローカルスタブのみを登録し、`execution: external` は呼び出し前に拒否する。環境変数、リクエスト、APIキーの存在による外部接続の有効化はない。外部AI用のSDK・通信処理もない。

案件名・顧客名・担当者名・連絡先・管理情報をプロバイダーに渡さない。制作に必要な11項目だけを渡し、登録済みの顧客名等の一致文字列、メール、電話、URLを除外する。秘密情報の兆候がある入力欄は全体を除外する。原本は編集しない。任意の人名・住所やあらゆる秘密を検出できる保証はない。将来の外部接続には送信内容の人間による確認、料金・データ保持条件の確認、明示承認を別途実装する。

スタブは依頼文から意図を推測しない。入力を出典付きで引用し、空欄・未定・不明・TBD・要確認・除外を不足情報と確認事項へ変換する。「不要」「なし」は入力済みとして扱う。引用は顧客の申告であり、実在する事実や実現可能性の保証ではない。各入力欄に補足して再分析する。

プロバイダー出力を保存前に検証する。事実・不足情報・質問は入力から決定的に作った内容と一致する必要があり、追加の事実、未知のキー、欠けた未確定事項は拒否する。提案は `proposed` の構造だけを許可し、仕様書の確定事項へ昇格させない。将来の意味解析対応時には、この厳格な契約を緩める前に根拠検証の設計・テストが必要。

### API・保存

- `POST /api/projects/:id/analyses`：空オブジェクトを受け付け、保存済み案件をローカル分析する。201で更新後の案件詳細を返す。
- `POST /api/projects/:id/specifications`：`{ "analysisId": "最新の分析ID" }` を受け付け、未承認の仕様書を保存する。
- `GET /api/projects/:id`：既存レスポンスを維持し、`analysisWorkspace` に分析・仕様書の全履歴、新しい順の版番号、更新検出フラグを追加する。

分析は `project_analyses.raw_json`、仕様書は `project_specs.content_json` に `schemaVersion: 1` で保存する。生成元分析ID・版・入力ハッシュを仕様書に保持し、旧形式は上書きしない。失敗した分析は保存せず、結果と履歴は同一トランザクションで保存する。実行中の同案件の二重分析、入力の更新、古い分析・別案件の分析からの生成を拒否する。入力ハッシュは制作項目と除外用の顧客情報に基づき、工程変更では古い扱いにしない。

エラーは400（入力）、403（外部送信・Origin）、404（案件なし）、409（更新・競合）、502（不正な分析出力）。予期しないプロバイダー例外の内容はログへ流さず汎用エラーに置き換える。

分析・生成は案件の工程や既存承認を変更しない。不足項目がゼロでも自動承認しない。仕様書は常に `draft`、採用済み提案は空であり、仕様書単位の承認・差し戻しは今回の範囲外。

### 検証

`npm run verify` で型チェック、既存API・永続化テスト、新規分析テスト、ビルドを実行する。新規テストは根拠の検証、秘密情報の除外、外部プロバイダー拒否、APIの入力・Origin・別案件チェック、失敗時の無保存と再試行、同時実行、編集競合、版管理、旧形式の保持、再起動後の保存を確認する。

## 目的

登録された案件を、制作仕様書を作れる状態へ整理する。

AIは顧客が提供していない事実を創作しない。推奨と事実を混同しない。

## AIへ送る情報

原則として制作判断に必要な情報だけを送る。

送信候補:

- 案件名
- 依頼内容
- サイト種類
- 制作目的
- ターゲット
- 必要ページ
- 希望デザイン
- 参考サイト
- 必要機能
- 掲載素材
- 希望納期
- 予算

原則送らない:

- 顧客のメールアドレス
- 電話番号
- 不要な個人名
- APIキー
- パスワード
- その他、制作分析に不要な秘密情報

必要になった場合だけ、人間が確認して送信対象を拡張する。

## AIの出力

AIの回答は自由文章だけではなく、構造化データとして保存する。

```json
{
  "summary": "",
  "purpose": "",
  "target": "",
  "requiredPages": [],
  "requiredFeatures": [],
  "designDirection": [],
  "cta": [],
  "seo": [],
  "responsiveNotes": [],
  "accessibilityNotes": [],
  "missingInformation": [],
  "customerQuestions": [],
  "productionNotes": [],
  "recommendations": []
}
```

## 絶対ルール

1. 入力にない会社情報、実績、料金、住所、人物情報を作らない。
2. 不明な情報は「不明」または `missingInformation` に入れる。
3. 顧客への確認が必要なものは `customerQuestions` に入れる。
4. AIの提案は事実ではなく `recommendations` として分離する。
5. 参考サイトの文章・デザインをそのままコピーしない。
6. 不要な機能を勝手に確定しない。
7. SEOキーワードを事実確認なしに「検索需要が高い」などと断定しない。
8. 納期や予算の実現可能性を断定せず、制作上の注意として示す。
9. 制作開始をAIが承認しない。
10. 顧客への連絡をAIが勝手に送信しない。

## 分析後のステータス

```text
新規
↓
AI分析中
├─ 必要情報が不足 → 情報不足
└─ 仕様作成に進める → 確認待ち
```

ステータス変更はAIの分析結果だけで重要判断を確定しない。必要に応じて人間が確認する。

## 制作仕様書へ渡す内容

AI分析が確定したら、以下を仕様書生成へ渡す。

- 確定している事実
- 顧客要望
- 承認済みの推奨案
- 未確定事項
- 禁止事項
- 制作上の注意

未確定事項は仕様書でも未確定のまま保持する。

## AI接続前の確認事項

- 利用するAIプロバイダー
- API料金
- データ利用・保持条件
- APIキーの保存方式
- 1案件あたりの送信量
- 再分析時のバージョン管理
- エラー時の再実行方針

これらを確認し、ユーザー承認後にAI APIを有効化する。
